# Онлайн-кинотеатр · аналитика событий

Python-проект для пунктов 1–5 ДЗ № 5 (7 баллов). Movie Service принимает JSON и публикует Protobuf в Kafka. ClickHouse читает топик, хранит события и считает дневные метрики. Отдельный сервис агрегации выгружает результаты в PostgreSQL.

- [Карта требований со ссылками на строки кода](docs/requirements.md)

## Запуск

Команда запуска из каталога с этим README

```sh
docker-compose up
```

Подойдёт и `docker compose up -d`. Нужен Docker Engine с Compose v2 или новее. При первом запуске Compose скачает образы и установит зависимости Python в контейнер. Kafka, реестр и обе базы используют постоянные тома. Сервисы `bootstrap` и `migrate` завершаются с кодом 0, после чего начинают работать оба API. По умолчанию генератор отправляет сессию каждые пять секунд, а агрегатор делает проход при старте и затем каждые пять минут после окончания предыдущего.

| Что открыть | Адрес или команда |
|---|---|
| Movie Service, форма публикации события | [Swagger UI](http://localhost:8000/docs) |
| Сервис агрегации, ручной пересчёт за дату UTC | [Swagger UI](http://localhost:8001/docs) |
| Protobuf-схема версии 1 | [Schema Registry](http://localhost:8081/subjects/movie-events-value/versions/1) |
| Журналы публикации и пересчёта | `docker compose logs -f movie-service aggregation-service` |
| Остановка с сохранением данных | `docker compose down` |

## Проверка одной командой

```sh
./test.sh
```

Скрипт создаёт отдельный проект Compose со своими томами и свободными портами. В нём генератор выключен, тесты сами отправляют события, а планировщик запускается с интервалом три секунды. После прогона скрипт удаляет тестовые контейнеры и тома. При ошибке он выводит последние строки журналов и возвращает ненулевой код.

Модульные тесты проверяют валидацию, бинарную сериализацию, порядок событий в сессии и прогресс. Интеграционные тесты проверяют реестр и топик, сравнивают все восемь полей между HTTP и ClickHouse, проверяют автоматическую выгрузку и сверяют метрики после ручного пересчёта в обеих БД. Среди проверок есть повтор одного события, повтор расчёта за тот же день и запоздалый просмотр.

## Проследить одно событие вручную

Следующие команды можно выполнять, когда оба API запущены. Фиксированная историческая дата позволяет увидеть именно этот пример независимо от даты запуска.

```sh
curl --fail-with-body http://localhost:8000/events \
  -H 'Content-Type: application/json' \
  -d '{"event_id":"3b4602e2-2be8-4d99-9716-23a96a80ebda","user_id":"reader","movie_id":"solaris","event_type":"VIEW_STARTED","timestamp":"2020-02-15T10:00:00.000Z","device_type":"TV","session_id":"reader-screening-1","progress_seconds":0}'

docker compose exec clickhouse clickhouse-client --user cinema --password cinema-local \
  --query "SELECT * FROM cinema.raw_events WHERE event_id = '3b4602e2-2be8-4d99-9716-23a96a80ebda' FORMAT Vertical"
```

HTTP 201 означает, что Kafka подтвердила запись. ClickHouse читает асинхронно. Когда строка появилась в `raw_events`, можно пересчитать показатели и посмотреть результат:

```sh
curl -fsS -X POST http://localhost:8001/recalculate/2020-02-15
docker compose exec postgres psql -U cinema -d cinema -c \
  "SELECT metric_name, dimension, value, computed_at FROM daily_metrics WHERE metric_date='2020-02-15' ORDER BY metric_name, dimension;"
```

В этом примере один зритель начал фильм и ещё не закончил. DAU равен 1, фильм `solaris` получил один просмотр, конверсия равна 0, а для среднего времени завершённого просмотра ещё нет наблюдений.

## Как устроен контракт

Клиент присылает UUID события и время с часовым поясом. Продюсер проверяет поля, нормализует время в UTC с точностью до миллисекунд и кодирует событие по [MovieEvent](schemas/movie_event.proto). UUID и время передаются в Protobuf строками, ClickHouse сохраняет их в типах `UUID` и `DateTime64(3, 'UTC')`. Для событий просмотра прогресс обязателен, включая ноль. Для поиска и лайка он отсутствует.

При старте регистрируется subject `movie-events-value`, версия 1, с политикой `BACKWARD_TRANSITIVE`. Продюсер сверяет файл по содержимому с реестром. В значении Kafka-записи лежит одно бинарное сообщение `ProtobufSingle`, а ID и версия схемы передаются в заголовках `schema-id` и `schema-version`. ClickHouse загружает ту же версию из файла схемы при старте. Изменение контракта требует согласованного обновления версии, Python-биндинга и схемы чтения ClickHouse.

У топика три партиции. Ключ `user_id` сохраняет порядок записи действий одного зрителя при неизменном числе партиций и распределяет аудиторию популярного фильма по нескольким партициям. Брокер в учебном стенде один, фактор репликации равен 1. Продюсер запрашивает `acks=all`. Повторная доставка в raw-таблицу возможна. Дневной расчёт учитывает каждый неизменный `event_id` один раз. Повторяя HTTP-запрос после таймаута, клиент передаёт исходный UUID и те же данные.

## Правила расчёта

Все даты — UTC. `processed` в журнале и ответе API — число различных событий за целевую дату. События предыдущих дней и дней возврата используются дополнительно для расчёта когорт.

| Метрика | Как читать результат |
|---|---|
| DAU | Число различных пользователей с любым событием за день, включая поиск или лайк. |
| Среднее время просмотра | Среднее `progress_seconds` только у `VIEW_FINISHED`. При отсутствии завершений — `NULL`. |
| Топ фильмов | До десяти фильмов по числу `VIEW_STARTED`. При равенстве первым идёт меньший `movie_id` в лексикографическом порядке. |
| Конверсия | Число завершений за день, делённое на число стартов за тот же день. При отсутствии стартов — `NULL`. Просмотр через полночь может дать конверсию выше 1. |
| Retention D1 и D7 | Когорта — зрители с первым за всю историю `VIEW_STARTED` в целевую дату. Возврат — хотя бы один `VIEW_STARTED` ровно через 1 или 7 календарных дней. Для пустой когорты или ещё не завершившегося дня наблюдения — `NULL`. |

ClickHouse хранит версионный снимок всей даты в `cinema.daily_metrics`. Актуальные строки доступны через `SELECT * FROM cinema.daily_metrics FINAL`. PostgreSQL хранит строки по ключу `(metric_date, metric_name, dimension)`. Для скалярных показателей `dimension` — пустая строка, для топа — идентификатор фильма. Retention хранится как доля от 0 до 1, конверсия — как отношение счётчиков. Блокировка по дате упорядочивает одновременные пересчёты. PostgreSQL получает целый дневной результат в одной транзакции.

Для учебного объёма планировщик заново обходит все даты, за которые уже есть события или агрегаты, и текущий день. Так поздно пришедший первый просмотр может исправить как прежнюю, так и новую когорту. Стоимость прохода растёт с объёмом истории.

## Параметры запуска

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `GENERATOR_INTERVAL_SECONDS` | 5 | Пауза между синтетическими сессиями в секундах, 0 выключает генератор. |
| `AGGREGATION_INTERVAL_SECONDS` | 300 | Пауза между проходами планировщика в секундах. |
| `MOVIE_PORT` | 8000 | Локальный порт API событий. |
| `AGGREGATION_PORT` | 8001 | Локальный порт API агрегации. |
| `REGISTRY_PORT` | 8081 | Локальный порт Schema Registry. |

Например, `GENERATOR_INTERVAL_SECONDS=0 AGGREGATION_INTERVAL_SECONDS=30 docker compose up -d` запускает стенд для ручной подачи событий с пересчётом каждые 30 секунд.
