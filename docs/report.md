# Отчёт по проектированию маркетплейса

Практика 1.2   Домашнее задание 1

## Цель и результат

Спроектирована архитектура маркетплейса с пятью доменными сервисами и отдельными владельцами данных. Подготовлена C4 Container диаграмма. Реализован технический каркас Orders Service на Python, который запущен в Docker на сервере hse и отвечает 200 OK на GET /health.

Работа разделяет проектирование и реализацию: каталог, оформление заказов, расчёт платежей, авторизация и отправка уведомлений описаны в архитектуре, но не реализованы в коде. Это соответствует ограничению задания об отсутствии бизнес-логики.

## Требования и принятые допущения

| Требование | Решение |
|---|---|
| Персональная лента | Catalog сортирует товары по выбранным категориям пользователя |
| Каталог продавца | Catalog владеет товарами, ценами, остатками и резервами |
| Покупатели и продавцы | Users хранит профили, роли, контакты и предпочтения |
| Оформление заказа | Orders хранит состав, снимки и жизненный цикл заказа |
| Расчёт и учёт платежей | Payments рассчитывает сумму и взаимодействует с PSP |
| Уведомления о статусе | Notifications обрабатывает события Orders |

Нагрузка, размер команды и SLA не заданы. Для проекта приняты одна валюта RUB и оплата на странице внешнего провайдера. Скидки, доставка, комиссии, выплаты продавцам и ML-рекомендации не входят в рассматриваемые правила. Эти допущения требуют уточнения при переходе к реальному продукту.

Лента сначала показывает товары выбранных категорий, затем остальные; внутри групп — новые товары первыми. Для гостя и при недоступности предпочтений используется обычная выдача. Так требование персонализации выполняется без отдельной рекомендательной платформы.

## Границы сервисов и владение данными

| Сервис | Ответственность | Собственные данные |
|---|---|---|
| Users | Пользователи и роли | Профили, контакты, предпочтения |
| Catalog | Каталог, лента, резервирование | Товары, цены, остатки, резервы |
| Orders | Заказы и координация процесса | Состав, исторические снимки, статусы |
| Payments | Расчёт, попытки, возвраты | Суммы, операции, статусы PSP |
| Notifications | Доставка и повторы | Шаблоны, задания, результаты отправки |

У каждого сервиса своя PostgreSQL БД и учётная запись. Чужой SQL, общие таблицы и межсервисные JOIN запрещены. Сервис изменяет только собственный источник данных. Orders хранит buyerId и снимок товара; эти копии не дают права менять Users или Catalog. Историческая цена заказа не меняется вслед за каталогом.

Каталог, цены и остатки объединены, чтобы атомарно создавать резерв с актуальной ценой. Простая персонализация использует тот же набор товаров. Payments выделен для учёта денежных состояний и интеграции с PSP. Notifications имеет собственные повторы и не должен блокировать оформление. Orders координирует процесс, сохраняя ответственность остальных владельцев.

## Представление C4

Полная диаграмма находится в docs/diagrams/container.svg и container.png; редактируемая модель — container.puml. На ней показаны покупатель и продавец, граница системы, Web UI, API Gateway, пять сервисов, пять БД, RabbitMQ и внешние провайдеры. У контейнеров указаны тип, технология и назначение; связи имеют направление, назначение и протокол.

C4 Container означает приложение или хранилище данных, а не обязательно Docker-контейнер. Диаграмма описывает целевую систему. Текущий Dockerfile запускает только Orders с health-check.

Web UI обращается к Gateway. Gateway маршрутизирует запросы и использует Users для проверки токена; права на конкретные объекты проверяют сервисы. Непосредственный ввод карточных данных происходит у PSP. Общей базы данных у приложений нет.

## Взаимодействия и оформление заказа

Синхронные HTTPS/JSON-запросы применяются там, где требуется немедленный результат: профиль, лента, проверка покупателя и резерв товара. Асинхронные сообщения RabbitMQ/AMQP связывают оформление, оплату и уведомления. Webhook PSP асинхронен относительно создания платежа, хотя сам доставляется HTTP-запросом.

1. UI передаёт идентификаторы товаров и количество. Orders проверяет пользователя через Users, запрашивает резерв и актуальный ценовой снимок у Catalog. Сумме из браузера доверять нельзя.
2. Catalog атомарно проверяет остатки и создаёт резерв с TTL. Orders сохраняет согласованный с покупателем снимок и OrderPlaced в локальной транзакции. При изменившейся цене нужно согласие покупателя.
3. Payments получает OrderPlaced и рассчитывает сумму как сумму произведений количества на цену в копейках. Он создаёт платёж у PSP и отправляет PaymentPending со ссылкой на оплату. UI получает ссылку через опрос Orders.
4. Результат оплаты подтверждает проверенный webhook PSP либо сверка с провайдером. Payments публикует PaymentSucceeded или PaymentFailed. Перенаправление браузера само по себе не подтверждает платёж.
5. Orders подтверждает или отменяет резерв через Catalog. После успешного подтверждения оплаченного заказа публикуется OrderStatusChanged. Notifications получает контакт из Users и отправляет сообщение через провайдера.
6. Если резерв истёк, Catalog сообщает ReservationExpired. Поздняя успешная оплата требует возврата: RefundRequested передаётся Payments, заказ ожидает RefundSucceeded. Неуспешный возврат остаётся в промежуточном состоянии до повторной попытки или разбора.

## Частичные сбои и согласованность

Общей транзакции между БД нет. Orders управляет процессом с компенсациями: освобождение резерва либо возврат денег. Неизвестный результат сетевого вызова уточняется повтором с тем же ключом. Тайм-аут не равен доказанному отказу операции.

Outbox сохраняет изменение и намерение отправить событие в одной локальной транзакции. Доставка допускает повторы; inbox и eventId защищают локальную обработку от повторного эффекта. Для PSP и отправки сообщений нужны отдельные ключи идемпотентности. Позднее событие не должно откатывать завершённое состояние. Все эти механизмы спроектированы, но не входят в реализованный каркас.

## Альтернативы и обоснование выбора

| Вариант | Плюсы | Минусы и цена выбора |
|---|---|---|
| Модульный монолит | Один релиз и отладка; локальные вызовы; простые транзакции | Масштабируется целиком; независимость модулей нужно поддерживать дисциплиной |
| Пять сервисов | Явные владельцы; отдельные релизы и ресурсы для платежей и уведомлений | Сеть, частичные сбои, компенсации и отложенная согласованность |
| Семь сервисов | Inventory и Feed развиваются и масштабируются отдельно | Дополнительные вызовы, проекции каталога, БД и контракты |

Выбран вариант с пятью сервисами. Он отражает разные процессы: жизненный цикл заказа, денежные операции и доставку сообщений. При этом простой ленте не нужен отдельный сервис, а объединение цен и резервирования уменьшает число распределённых операций. Решение зафиксировано в ADR-001.

Выбор имеет цену: выше затраты на эксплуатацию и восстановление после сбоев. При неизвестных нагрузке и составе команды нельзя утверждать, что микросервисы объективно дешевле. Для небольшого реального MVP модульный монолит был бы разумным стартом. Здесь пять сервисов выбраны для явного проектирования ответственности, независимого учёта платежей и асинхронной обработки уведомлений.

Выделять Feed стоит после усложнения рекомендаций или появления независимой нагрузки; Inventory — при развитии складского учёта. Числовые пороги без измерений не задаются. Если независимые релизы не нужны, архитектуру следует упростить.

## Ограничения реализации

В коде отсутствуют модели товаров и заказов, SQL, платёжные SDK, обработчики событий и бизнес-маршруты. GET /health возвращает JSON со статусом ok и именем orders. Неизвестные GET-пути возвращают 404. Стандартная библиотека Python позволяет обойтись без установки зависимостей.

Контейнер запускается от UID 10001, имеет встроенный HEALTHCHECK и публикует только локальный порт хоста. Health-check проверяет доступность процесса; после появления БД и брокера потребуется отдельно определить readiness. Учебный http.server не рассматривается как окончательный промышленный HTTP-стек.

## Проверка и воспроизведение

Проверка выполнена 26 сентября 2026 года на hse в ~/soa/hw1. Docker Engine 29.1.3; Python 3.10.12 на хосте и 3.13.15 в контейнере. Полный протокол и логи находятся в docs/verification.md и docs/verification/.

| Проверка | Результат |
|---|---|
| Два HTTP-теста | OK |
| Сборка Dockerfile | Успешно |
| Запуск контейнера | running |
| Встроенный HEALTHCHECK | healthy |
| GET /health на порту 18080 | 200 OK и ожидаемый JSON |
| GET /orders, /payments, /missing | 404 |

Минимальные команды для чистого окружения:

```bash
docker build -t soa-hw1-orders:local .
docker run -d --name soa-hw1-orders \
  -p 127.0.0.1:18080:8080 soa-hw1-orders:local
curl -i http://127.0.0.1:18080/health
docker inspect --format '{{.State.Health.Status}}' soa-hw1-orders
```

Ожидаемый JSON: {"status":"ok","service":"orders"}. Для остановки: docker stop soa-hw1-orders; затем docker rm soa-hw1-orders. Полные команды с ограничениями контейнера и вариант SSH-туннеля приведены в README.

Compose-конфигурация и GitHub Actions подготовлены, но их запуск на hse не проверен: плагин Compose отсутствует. Успешно проверен основной путь через docker build и docker run. Бизнес-сценарии и нагрузка не тестировались, поскольку бизнес-логика по условию отсутствует.
