# Подготовка к защите

## Доклад на 4–5 минут

Текст рассчитан на спокойное объяснение с показом диаграммы. Говорите о бизнес-процессах как о проекте: в коде реализована только проверка состояния сервиса.

> Я спроектировал архитектуру маркетплейса, в котором продавцы управляют товарами, а покупатели получают персональную ленту, оформляют и оплачивают заказы. Задание ограничивает реализацию: бизнес-логики быть не должно. Поэтому результат состоит из архитектурного проекта и минимального сервиса Orders с GET /health. Границы между спроектированным и реализованным я явно обозначил в документации.
>
> На C4 Container диаграмме показаны покупатель и продавец, веб-интерфейс, API Gateway, пять доменных сервисов, принадлежащие им базы данных и брокер RabbitMQ. Платёжный провайдер и провайдер уведомлений находятся за границей маркетплейса. Container в C4 означает приложение или хранилище данных. Это уровень логической архитектуры, поэтому контейнер C4 не обязательно соответствует одному Docker-контейнеру.
>
> Users отвечает за пользователей, роли и предпочтения. Catalog владеет товарами, ценами, остатками и резервами. Здесь же формируется простая персональная лента: товары из предпочтительных категорий получают приоритет. Для такой персонализации отдельный рекомендательный сервис пока не нужен. При отсутствии предпочтений можно показывать общую ленту.
>
> Orders владеет заказами и снимками их состава. Он координирует оформление заказа. Payments рассчитывает итоговую сумму по доверенному снимку заказа, учитывает попытки и статусы платежей и взаимодействует с платёжным провайдером. Notifications обрабатывает события о статусах заказов и управляет отправкой сообщений. API Gateway служит единой точкой входа, но не принимает доменные решения.
>
> Каждый доменный сервис имеет собственную PostgreSQL. Другие сервисы не читают её таблицы напрямую. Например, заказ хранит идентификатор товара и снимок его названия и цены. Это допустимое дублирование: Catalog хранит текущие сведения, а Orders — условия конкретной покупки. Наличие одинаковых идентификаторов не означает общей базы данных.
>
> Синхронные запросы нужны там, где вызывающей стороне необходим немедленный ответ: например, при проверке и резервировании доступного количества товара. После сохранения заказа событие OrderPlaced запускает обработку в Payments. Ссылка на страницу оплаты приходит в Orders через событие PaymentPending; интерфейс получает её, опрашивая заказ. После результата платежа Orders меняет статус и публикует событие для Notifications. Такой выбор даёт независимую обработку, но означает, что состояние разных сервисов может обновляться с задержкой.
>
> В проекте я учитываю сбои. Резерв должен создаваться атомарно в Catalog, иначе два покупателя могут одновременно приобрести последний товар. Цена фиксируется в согласованном снимке заказа, а сумма из браузера не считается доверенной. При изменении цены OrderPlaced появляется в outbox только после подтверждения покупателем. События могут доставляться повторно, поэтому обработчики должны быть идемпотентными. Для надёжной публикации предлагается transactional outbox; для потерянного ответа платёжного провайдера — сверка статуса операции. Это проектные решения, а не реализованные механизмы.
>
> Я сравнил выбранную архитектуру с модульным монолитом. Монолит проще запускать и сопровождать, а локальные транзакции облегчают согласованность данных. Для небольшого реального MVP я рассматривал бы его первым. Пять сервисов требуют брокера, сетевых вызовов и обработки частичных отказов, зато дают явное владение данными и независимые границы платёжной и уведомительной обработки. Для этого учебного проекта я выбрал пять сервисов, чтобы показать эти границы и аргументировать взаимодействия. Я не выделял сервис на каждую сущность: товары, цены и остатки пока остаются внутри одного домена Catalog.
>
> В конце я покажу реализованную часть: сборку образа командой docker build, запуск Orders командой docker run и проверку GET /health. Этот результат подтверждает работоспособность каркаса сервиса. Он не доказывает готовность архитектуры к промышленной нагрузке и не заменяет будущую реализацию бизнес-процессов.

## Демо: Docker Engine без Compose

На hse 26 сентября 2026 года подтверждены Docker-запуск, состояние `healthy` и HTTP 200 OK. Фактически выполненные команды и результаты собраны в [протоколе проверки](verification.md). Приведённые ниже команды — сценарий демонстрации; результат подтверждается их выводом.

Подключитесь к серверу и перейдите в корень проекта:

```bash
ssh hse
cd ~/soa/hw1
```

При первом запуске соберите образ и создайте контейнер. Если контейнер `soa-hw1-orders` уже работает после проверки проекта, перейдите сразу к проверке состояния и запросу `curl`: повторный `docker run` с тем же именем не нужен.

```bash
docker build -t soa-hw1-orders:local .
docker run -d --name soa-hw1-orders \
  --read-only --cap-drop=ALL \
  --security-opt no-new-privileges:true \
  -p 127.0.0.1:18080:8080 \
  soa-hw1-orders:local
```

После запуска проверьте состояние контейнера и ответ сервиса:

```bash
docker inspect --format '{{.State.Status}} / {{.State.Health.Status}}' soa-hw1-orders
curl -i http://127.0.0.1:18080/health
docker logs --tail=30 soa-hw1-orders
```

Ожидаемые результаты: состояние `running / healthy` и статус `200 OK` в ответе `curl`. Сразу после запуска healthcheck может ещё показывать `starting`; повторите `docker inspect` через несколько секунд. Адрес `127.0.0.1` относится к серверу: запрос нужно выполнять в открытой SSH-сессии. Порт `18080` на сервере перенаправляется на порт `8080` контейнера.

Покажите обработчик в `services/orders/app.py`: сервис запускает HTTP-сервер и обрабатывает путь `/health`; базы данных, заказы и платежи в коде не реализованы. Объясните, что `healthy` подтверждает именно настроенную проверку `/health`, а не готовность всего маркетплейса.

После демонстрации остановите и удалите только созданный для этого проекта контейнер:

```bash
docker rm -f soa-hw1-orders
```

Образ и исходные файлы сохранятся. Для следующего показа контейнер можно создать той же командой `docker run`. Если запрос не проходит, сначала покажите `docker logs` и `docker inspect`; не объявляйте проверку успешной без фактического ответа.

### Опционально: запуск через Compose

Этот вариант подходит для машины с установленными плагинами Docker Compose и buildx. Основной сценарий выше их не требует. Перед переходом на альтернативу завершите предыдущую демонстрацию, чтобы освободить порт `18080`.

```bash
PORT=18080 docker compose up --build --wait --wait-timeout 60
docker compose ps
curl -i http://127.0.0.1:18080/health
docker compose logs --tail=30 orders
docker compose down
```

Для защиты достаточно одного подтверждённого запуска в Docker. Сборка образа может потребовать доступ к реестру образов. Запуск Python без контейнера не заменяет обязательную проверку Docker.

## Вопросы преподавателя и короткие ответы

1. **Что именно реализовано?** Только каркас Orders и GET /health. Все остальные компоненты и бизнес-процессы описаны как целевая архитектура.

2. **Почему это C4 Container?** Диаграмма показывает исполняемые приложения, хранилища, технологии и связи внутри системы. Классы и функции относятся к более подробным уровням.

3. **Container C4 равен Docker-контейнеру?** Нет. C4 описывает архитектурную единицу, Docker — способ упаковки и запуска. Один C4-сервис может иметь несколько экземпляров Docker.

4. **Зачем пять сервисов?** У них разные зоны ответственности и владельцы данных. Это учебный выбор для демонстрации границ; для маленькой команды монолит мог бы быть дешевле.

5. **Почему не сервис на каждую сущность?** Сущность не равна независимому домену. Излишнее дробление увеличивает число сетевых вызовов и распределённых операций без ясной выгоды.

6. **Почему лента находится в Catalog?** Персонализация ограничена предпочтительными категориями и использует каталог. Самостоятельный сервис оправдан при усложнении алгоритма, данных или требований к масштабированию.

7. **Что показывать новому пользователю?** Общую ленту. Это явно выбранное поведение при отсутствии предпочтений, не результат обученной модели рекомендаций.

8. **Может ли Orders прочитать таблицы Catalog?** Нет. Только публичный API или события. Иначе сервисы связываются внутренними схемами и не могут независимо менять данные.

9. **Идентификатор пользователя в заказе нарушает независимость баз?** Нет. Это ссылка по значению, а не межбазовый внешний ключ. Её корректность обеспечивается контрактом взаимодействия.

10. **Зачем дублировать цену в заказе?** Снимок фиксирует условия покупки. Изменение текущей цены товара не должно переписывать историю оформленного заказа.

11. **Что, если цена изменилась во время оформления?** Catalog возвращает актуальные условия при резервировании. При изменении цены Orders запрашивает явное согласие покупателя. До него заказ находится в QUOTED и OrderPlaced отсутствует в outbox; после согласия и проверки резерва AWAITING_PAYMENT и событие сохраняются одной транзакцией. При отказе резерв освобождается.

12. **Кто защищает последний товар от двойной продажи?** Catalog атомарно проверяет и резервирует доступное количество в своей транзакции. Проверка остатка без резерва оставляет гонку.

13. **Кто рассчитывает платёж?** Payments по доверенному снимку из Orders. Catalog задаёт цены, Orders фиксирует состав покупки; значения из браузера не являются основанием списания.

14. **Почему часть взаимодействий синхронная?** Для решения, которое требуется прямо сейчас, нужен немедленный ответ. Цена этого выбора — зависимость от доступности вызываемого сервиса и необходимость тайм-аутов.

15. **Почему уведомления асинхронные?** Заказ не должен ждать почтового или другого провайдера. Брокер позволяет обработать событие позже, но требует повторов и защиты от дубликатов.

16. **RabbitMQ гарантирует однократную обработку?** Нет. При повторной доставке возможны дубликаты. Бизнес-эффект защищают идентификаторы событий, уникальные ограничения и идемпотентные обработчики.

17. **Что решает transactional outbox?** Запись бизнес-изменения и события выполняется в одной локальной транзакции. Фоновый издатель сервиса повторяет публикацию события; дубликаты всё равно возможны.

18. **Что такое inbox?** Учёт уже обработанных событий у получателя. Запись идентификатора события и локальный эффект нужно фиксировать согласованно, чтобы повтор не выполнил действие заново.

19. **Провайдер списал деньги, но ответ потерялся. Что делать?** Проверить статус операции по её устойчивому идентификатору. Повторный запрос использует тот же ключ идемпотентности; нельзя безусловно создавать новое списание.

20. **Платёж учтён, но событие не дошло до Orders. Что делать?** Outbox повторяет публикацию; Orders безопасно обрабатывает повтор. Неопределённые состояния дополнительно выявляются сверкой. Уведомление пользователю не является источником истины.

21. **Можно сделать общую транзакцию пяти баз?** В выбранном проекте её нет. Используются локальные транзакции и координация шагов; при неуспехе нужны компенсации, например освобождение резерва.

22. **Что значит eventual consistency?** После успешного локального изменения другие сервисы могут некоторое время видеть старое состояние. При восстановлении обработки события доводят их до согласованного состояния.

23. **Что, если RabbitMQ недоступен?** Outbox сохраняет ожидающие публикации события. Асинхронные шаги задерживаются; нужны повторы, мониторинг накопления и политика ограничения очереди. Эти механизмы пока не реализованы.

24. **Чем health отличается от readiness?** Liveness показывает, что процесс отвечает; readiness — что экземпляр готов обслуживать рабочие запросы. Текущий /health — минимальная проверка живого HTTP-сервера без зависимостей.

25. **Что вы действительно проверили?** Покажу команды и результаты из [протокола проверки](verification.md), а затем повторю проверку контейнера и /health. Наличие Dockerfile само по себе не доказывает запуск; проектные схемы не доказывают реализацию, производительность или отказоустойчивость.

## Шпаргалка понятий — один лист

| Понятие | Что помнить на защите |
|---|---|
| Домен | Область бизнес-ответственности: пользователи, каталог, заказы, платежи, уведомления. |
| Сервис | Приложение с определённой ответственностью и публичным контрактом. |
| C4 Context / Container | Context: система и окружение. Container: приложения, хранилища и связи. |
| Владелец данных | Единственный сервис, определяющий правила записи и изменения своих данных. |
| Снимок | Сохранённые условия конкретной покупки; не копия текущего каталога для редактирования. |
| Синхронный вызов | Вызывающая сторона ждёт ответ; важны тайм-ауты и обработка ошибок. |
| Событие | Сообщение о произошедшем факте; потребители могут обработать его позже. |
| Идемпотентность | Повтор одной операции не создаёт повторного бизнес-эффекта. |
| Outbox / inbox | Outbox защищает публикацию после локальной записи; inbox помогает отсеять повторную обработку. |
| Резерв | Временно закреплённое количество товара; нужны срок жизни и правила освобождения. |
| Компенсация | Новое действие, исправляющее последствия предыдущего шага; не откат общей транзакции. |
| Eventual consistency | Изменения доходят до разных сервисов с задержкой при работоспособной доставке. |
| PSP | Внешний провайдер платежей. Данные банковских карт не входят в модель учебного сервиса. |
| Liveness / readiness | «Процесс отвечает» / «экземпляр готов принимать рабочие запросы». |
| Главный trade-off | Ясные автономные границы против сложности распределённых вызовов и согласованности. |

Безопасная формулировка при вопросе за рамками проекта: «В этом ДЗ механизм не реализован. Я предусмотрел такой подход; перед реализацией уточнил бы контракт и проверил сценарии отказа».
