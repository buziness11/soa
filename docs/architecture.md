# Архитектура маркетплейса

## Статус и границы работы

Это проект целевой архитектуры. Реализован только каркас Orders Service с `GET /health`, подготовлены Dockerfile и инструкция запуска. Каталог, заказы, платежи, авторизация, БД и обмен событиями **не реализованы**. Описанные ниже механизмы — решения для будущей разработки. Факт локальной проверки Docker следует смотреть в отчёте: наличие Dockerfile само по себе не подтверждает запуск контейнера.

Кейс требует ленту товаров, работу продавцов с каталогом, управление покупателями и продавцами, оформление заказов, расчёт и учёт платежей, уведомления. Доставка, поиск по тексту, рекомендации на ML, мультирегиональность и хранение изображений не входят в работу.

Кейс не задаёт нагрузку, размер команды или SLA. Допускаем одну валюту RUB, оплату через внешнего платёжного провайдера и простую персонализацию по явно выбранным категориям. Товары могут принадлежать разным продавцам. Расчёт комиссий, распределение выплат продавцам и логистические подзаказы требуют отдельных правил и здесь не проектируются. Эти допущения нельзя выдавать за реальные бизнес-требования.

## Контейнеры и домены

Покупатель и продавец используют Web UI. Он обращается к API Gateway по HTTPS. Gateway маршрутизирует запросы и ограничивает частоту обращений; для защищённых операций проверяет токен через auth_request к Users. Публичное чтение каталога и гостевая лента доступны без обязательной авторизации. При отказе Users для публичной выдачи применяется гостевой режим, а защищённые операции отклоняются; доменных правил у Gateway нет. Сервисы дополнительно проверяют права на конкретные объекты. В целевой схеме внутренние синхронные вызовы идут по HTTPS/JSON. Локальный учебный health-check использует HTTP.

| Сервис | Домены и ответственность | Собственные данные |
|---|---|---|
| Users | Пользователи: профили, роли покупателя/продавца, контакты, предпочтения категорий | Пользователи, роли, контакты и предпочтения |
| Catalog | Каталог: товары и цены; товарные остатки и резервы; персональная лента | Карточки, категории, `sellerId`, актуальные цены, доступные остатки, резервы с TTL |
| Orders | Заказы: состав, жизненный цикл и координация оформления | Заказы, `buyerId`, снимки позиций, состояние оформления, ключи идемпотентности |
| Payments | Платежи: расчёт суммы по подтверждённому снимку, попытки оплаты, статусы, возвраты, интеграция с PSP | Денежные суммы, попытки, ссылки на заказы, идентификаторы PSP, результаты оплаты и возвратов |
| Notifications | Уведомления: шаблоны, доставка и повторные попытки | Шаблоны, задания доставки, канал, статус, ключи дедупликации |

Каждый сервис владеет отдельной PostgreSQL БД, миграциями и учётными данными. Запрещены чужой SQL, общие таблицы, межсервисные JOIN и внешние ключи между БД. Размещение БД на одном физическом сервере допустимо как эксплуатационное решение, но не даёт сервисам доступ к чужим данным.

Владение означает право изменять первоисточник. `sellerId` в Catalog и `buyerId` в Orders — ссылки на идентификаторы Users, а не право менять пользователей. Название и цена в позиции заказа — неизменяемый исторический снимок Catalog: последующая смена цены товара не меняет заказ. Состояние платежа в Orders — проекция Payments. Получатель в задании Notifications — копия контакта для конкретной доставки; актуальный контакт принадлежит Users.

Web UI, Gateway, RabbitMQ и пять БД также показаны на Container-диаграмме. Внешние системы — PSP и провайдер email/push. Контейнер C4 означает приложение или хранилище данных; он не обязан соответствовать Docker-контейнеру. Диаграмма показывает целевую систему, тогда как Docker-конфигурация этого ДЗ запускает один сервис.

## Почему домены распределены так

Каталог, цены и остатки объединены: резерв должен атомарно проверить количество и зафиксировать согласованную цену. Лента использует те же товары; выделять отдельный рекомендательный сервис для сортировки по категориям пока невыгодно. Users хранит предпочтения, Catalog применяет их к выдаче: сначала товары выбранных категорий, затем остальные; внутри групп — новые товары первыми. При недоступности Users доступна обычная лента.

Orders управляет ходом заказа, но не редактирует остатки и не проводит платежи. Payments выделен из-за внешнего PSP, собственных денежных состояний и требований к аудиту. Notifications выделен, чтобы сбои доставки и повторные попытки не мешали оформлению. Users отделён как единый владелец профилей и контактов покупателей и продавцов.

## Взаимодействия

| Инициатор → получатель | Способ | Назначение |
|---|---|---|
| Web UI → Gateway → соответствующий сервис | Синхронный HTTPS/JSON | Профиль, каталог, лента, оформление, просмотр своих заказов и их платёжного статуса через Orders |
| Catalog → Users | Синхронный HTTPS/JSON | Предпочтения для ленты, проверка роли продавца при изменении каталога |
| Orders → Users | Синхронный HTTPS/JSON | Проверка существования и доступности покупателя |
| Orders → Catalog | Синхронный HTTPS/JSON | Создание, подтверждение и отмена резерва; получение ценового снимка |
| Orders → RabbitMQ → Payments | Асинхронные сообщения | `OrderPlaced`, команда `RefundRequested` при компенсации |
| Payments → PSP | Синхронный HTTPS | Создание платежа или возврата с ключом идемпотентности |
| PSP → Payments | Асинхронный HTTPS webhook | Подтверждённый результат; подпись и сумма проверяются |
| Payments → RabbitMQ → Orders | Асинхронные события | `PaymentPending` с `payment_url`, `PaymentSucceeded`, `PaymentFailed`, `RefundSucceeded` |
| Web UI → PSP | HTTPS, переход на hosted checkout | Ввод платёжных данных на стороне провайдера |
| Catalog → RabbitMQ → Orders | Асинхронное событие | `ReservationExpired` |
| Orders → RabbitMQ → Notifications | Асинхронное событие | `OrderStatusChanged` |
| Notifications → Users | Синхронный HTTPS/JSON | Чтение контакта и разрешённого канала |
| Notifications → провайдер email/push | Синхронный HTTPS | Отправка; факт приёма провайдером отделён от факта доставки |

RabbitMQ переносит сообщения, но не служит источником истины для заказов или платежей. Команда требует действия конкретного получателя, событие сообщает о совершившемся факте. Все перечисленные связи относятся к проекту.

## Оформление заказа и ошибки

1. Браузер передаёт идентификаторы товаров, количество и ключ идемпотентности. `buyerId` берётся из проверенной идентичности. Цены и итоговая сумма из браузера не принимаются как достоверные.
2. Orders создаёт запись оформления с `orderId`, проверяет покупателя в Users и запрашивает резерв Catalog с тем же `orderId`. Catalog одной локальной транзакцией проверяет остатки, создаёт резерв и возвращает снимок товаров с ценами, валютой и сроком резерва. Повтор запроса возвращает тот же результат.
3. Orders сохраняет предложенный снимок в состоянии `QUOTED`, без `OrderPlaced` в outbox. Если цена изменилась относительно показанной покупателю, требуется явное согласие с новой суммой; при отказе резерв освобождается. После согласия и проверки действительности резерва Orders одной транзакцией фиксирует подтверждённый снимок, `AWAITING_PAYMENT` и `OrderPlaced` в outbox. Фоновый издатель не может отправить заказ до согласия, потому что события ещё нет в таблице. Незавершённый резерв освобождается по TTL.
4. Payments получает событие и рассчитывает сумму как сумму `quantity × unitPrice` по подтверждённому снимку. Деньги хранятся целым числом копеек, валюта — отдельным полем. Скидки, доставка и комиссии в этой модели отсутствуют. Payments сохраняет попытку и обращается к PSP с устойчивым ключом идемпотентности. Событие `PaymentPending` передаёт Orders ссылку `payment_url`. UI периодически запрашивает состояние своего заказа через Gateway → Orders и получает ссылку для перехода на hosted checkout PSP. Карточные данные маркетплейс не хранит. Результат перенаправления браузера не подтверждает оплату: нужен проверенный webhook либо сверка с PSP.
5. После `PaymentSucceeded` Orders просит Catalog подтвердить резерв. Catalog атомарно превращает активный резерв в списание; повтор подтверждения безопасен. Только после успешного подтверждения Orders переводит заказ в `PAID` и публикует `OrderStatusChanged`. Notifications получает событие и создаёт задание доставки.
6. При отказе оплаты Orders отменяет заказ и освобождает резерв. При истечении TTL Catalog публикует `ReservationExpired`; Orders закрывает неоплаченное оформление. Поздняя успешная оплата при уже истёкшем резерве приводит к `REFUND_PENDING` и команде `RefundRequested`. После подтверждённого возврата заказ становится `REFUNDED`. Нельзя просто забыть успешно списанные деньги.

Между пятью БД нет общей транзакции. Здесь используется оркестрация в Orders с компенсациями: освобождением резерва или возвратом платежа. При неизвестном результате сетевого вызова Orders повторяет операцию с прежним ключом и уточняет её состояние; тайм-аут сам по себе не означает отказ оплаты или резерва. Пока подтверждение резерва не выяснено, заказ остаётся в промежуточном состоянии, а не объявляется оплаченным.

Публикация сообщения может повториться: доставка — **at least once**. Проект предусматривает transactional outbox у отправителя и inbox/уникальный `eventId` у потребителя. Outbox — таблица в собственной БД сервиса и работающий в нём фоновый издатель, а не отдельный сервис или обязательный дополнительный деплой. Изменение локального состояния и отметка обработанного события выполняются одной транзакцией. Для внешнего эффекта нужны отдельные ключи идемпотентности PSP/провайдера; inbox сам по себе не исключает повторную отправку письма после сбоя между отправкой и записью результата.

Повтор HTTP-запроса с тем же ключом и тем же телом возвращает прежний результат; другое тело с тем же ключом отклоняется. Одновременно допускается одна активная попытка оплаты заказа; события платежей содержат её идентификатор. События также содержат `eventId`, `orderId`, тип, версию схемы и время. Переходы состояний проверяются, позднее сообщение не откатывает заказ назад. При необходимости сравнивается версия одного и того же агрегата, а спорные состояния сверяются с владельцем данных. Повторы ограничены, неуспешные сообщения попадают в dead-letter queue для разбора. Неуспешный возврат остаётся в `REFUND_PENDING` и требует повторов или ручного разбора. Сбой уведомления не отменяет заказ; пользователю доступен его статус через API.

## Что усложнилось и что проверять дальше

Разделение позволяет менять платежи и доставку уведомлений независимо, но добавляет сеть, отложенную согласованность и восстановление после частичных сбоев. При развитии проекта понадобятся контрактные тесты API/событий, проверки повторной оплаты, гонки оплаты с истечением резерва и восстановления outbox. Понадобятся метрики и корреляция по `orderId`. Для текущего ДЗ проверяются только запуск сервиса и ответ `/health`; эти будущие проверки не заявлены как выполненные.
